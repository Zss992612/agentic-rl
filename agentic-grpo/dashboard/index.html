07

FAILURE LOG

真正塑造项目的几个问题

面试时不只讲“修了什么”，还要讲观察、排除路径和系统性影响。

01
训推 Chat Template 协议错位模型不调用工具、重复回复、错误拒绝
已解决

根因：训练目标是 assistant header → tool_call，而在线推理变成 assistant header → empty think → tool_call。

判断依据：NPY 数据审计确认工具调用和 labels 完整；仅替换模板就让结果从约 0.06 恢复。

修复：固定自定义 no-think 模板，并把 Chat Template 视为模型协议的一部分。

02
User API 空响应终止整个 StepStep 46 中断，模型只能回到 checkpoint 40
已缓解

根因：API 返回 final chunk，但 content 为空；UserMessage 校验异常通过 asyncio gather 传播到整个 batch。

修复：同一 user turn 使用原状态原地重试一次；仍失败才标记基础设施错误，轨迹级重试作为最后防线。

剩余风险：五小时 API 额度约支持 55–56 step，真正耗尽时重试不能创造额度。

03
长序列 Actor 更新过慢显存未满不代表还能线性加速
已优化

根因：padding、全 token vocab projection、注意力和反向传播共同放大计算量；瓶颈最终落在 FLOPs，而非显存容量。

修复：remove padding、FlashAttention、Assistant-only LM Head、动态 token micro-batch。

04
模型错误与基础设施错误混在一起错误奖励会污染 GRPO 优势
已分层

模型错误：错误工具参数、重复操作、超过最大步数，可以得到 reward 0。

环境/API 错误：超时、空响应、网关故障，不应当作为模型失败进入训练。

05
Checkpoint 与 W&B 时间线分叉日志到 Step 45，但最近模型状态只有 Step 40
已处理

恢复时重新计算 Step 41–45，并新建 W&B Run，避免两套不同模型状态共享同一组 step 编号。

30-SECOND PITCH

我在 τ²-bench Retail 上构建了一个面向长链路、多工具 Agent 的强化学习系统。项目先用 256 条高质量轨迹对 Qwen3-4B 做 Assistant-only LoRA SFT，将 Pass¹ 提升到 69.375%；随后基于 VERL、vLLM 和自定义异步 AgentLoop 跑通 4×8 Vanilla GRPO，并围绕长序列计算、API 长尾、错误归因和 checkpoint 恢复做了系统优化。当前目标是在可靠二元奖励基线上研究更细粒度的长轨迹信用分配。
01 · WHY

为什么做

最终二元奖励很难说明长轨迹中哪一步真正贡献了成功或失败。

LIKELY FOLLOW-UPS

高频追问

为什么先用二元奖励，而不是直接设计过程奖励？

先固定一个可复现的基线，避免把系统错误、环境问题和奖励设计同时引入。只有看到 Vanilla GRPO 的真实失败模式，细粒度奖励才有明确靶点。

为什么选择 GRPO，而不是带 Critic 的 PPO？

同一任务可以自然采样多个 rollout，组内相对奖励直接提供优势估计；同时避免训练额外价值模型，适合当前 4B 模型与单卡资源。

为什么使用 vLLM 而不是 SGLang？

VERL 对 vLLM 的训练集成更成熟，权重同步与 rollout correction 路径更直接；当前瓶颈主要是外部 User API，而不是缺少更复杂的推理调度。

这个项目最有价值的工程发现是什么？

Chat Template 不是展示格式，而是模型协议。一个空 think 前缀就能让正常下降的 SFT loss 与在线 Agent 能力彻底脱节。

下一步信用分配准备怎么做？

完成 Vanilla 基线后，优先从实际失败中选择一到两个信号，例如可验证的 progress reward 或工具状态变化，而不是同时堆叠多个奖励。
