长轨迹 Agent 强化学习项目笔记

记录已经验证的内容；边复盘、边理解、边补充。

01 · 项目概览

Project Overview

这个项目研究的是：在 τ²-bench Retail 的长链路、多工具交互任务中，怎样训练一个能够理解用户意图、读取环境、调用工具并正确修改数据库的 Qwen3-4B Agent。

1.1 核心问题

一条 Retail 轨迹通常包含几十轮对话、多个读取操作和若干可能改变数据库的写操作。环境最终只返回成功或失败，因此最终奖励无法直接说明中间哪一个 Assistant turn 做对了、哪一个动作造成了失败。这就是本项目真正要处理的长轨迹信用分配问题。

1.2 研究策略

项目并没有从复杂奖励函数开始，而是先建立可工作的 SFT 与 Vanilla GRPO 基线，再根据真实失败轨迹逐步修改训练信号。整个过程依次经历了数据构建、协议排错、训练基础设施优化、第一版局部奖励实验，以及最终的 Anchored Turn GRPO。

数据与 SFT → 在线 Agent 训练 → Vanilla GRPO → 失败归因 → 细粒度信用分配

当前理解：项目的价值不只在于跑通 GRPO，而在于形成了“发现问题—修改实现—控制实验—统一评测—配对归因”的完整研究闭环。

Research Thread

这里暂时只记录改变项目方向的关键节点。每个节点的实现细节、数据流和公式将在后续复盘时逐段补入。

    构建 SFT 数据与 Agent 基线

    从 512 条候选轨迹中筛选 256 条成功轨迹，覆盖 64 个训练任务；使用 Assistant-only Loss 完成 LoRA SFT。

    Data · SFT
  2. 2.2

    定位 Chat Template 协议错位

    空 think 前缀改变了模型学习到的工具调用 token 协议，使在线模型无法正确发起工具调用。统一 no-think 模板后，工具能力恢复。

    Protocol
  3. 2.3

    跑通 Vanilla GRPO 系统

    接入 VERL、vLLM、FSDP 与异步 AgentLoop，形成 4 tasks × 8 rollouts 的单卡在线训练流程。

    Training System
  4. 2.4

    解决长序列训练瓶颈

    引入 remove padding、FlashAttention varlen、Assistant-only LM Head、动态 micro-batch 和 rollout log-prob bypass，降低冗余计算并提高训练吞吐。

    AI Infra
  5. 2.5

    第一版 Potential GRPO 暴露问题

    直接把局部进度和固定错误惩罚叠加到 outcome advantage 上，会改变原始训练信号的尺度，甚至让失败轨迹中的局部动作获得错误方向的更新。

    V1 · Lesson
  6. 2.6

    提出 Anchored Turn GRPO

    新方案只在成功轨迹内部重新分配信用，并保持 outcome advantage 的符号和 token 加权均值，避免局部奖励覆盖最终任务目标。

    V2 · Method
  7. 2.7

    统一评测与配对错误归因

    在相同 User API、任务、trial 和 seed 下比较 SFT、Vanilla 与 Anchored，再逐条检查成功翻转和回归轨迹的决定性差异。

    Evaluation

03 · 当前证据

Current Evidence

统一使用 DeepSeek 官方 User API，在 40 个测试任务上各采样 4 次。Anchored step80 共成功 114/160 次，Pass¹ 为 71.25%；完全失败任务从 5 个减少到 2 个。

模型 成功 Pass¹ Pass² Pass³ Pass⁴
SFT step96 106 / 160 66.25% 52.50% 43.75% 37.50%
Vanilla step100 109 / 160 68.12% 55.83% 48.75% 45.00%
Anchored step80 114 / 160 71.25% 54.17% 41.88% 32.50%

3.1 当前结果说明了什么

Anchored 提高了单次采样的成功覆盖率，也让一部分原本完全不会做的困难任务变得可解；与此同时，4/4 稳定成功任务减少，说明当前方法在覆盖率与重复采样可靠性之间仍存在权衡。

配对归因：在 23 条 Vanilla 失败、Anchored 成功的轨迹中，必需写操作遗漏由 7 条降至 0 条，非目标写操作由 6 条降至 2 条。改善主要表现为更好的写前决策、动作顺序和实体绑定，而不是单纯增加工具调用次数。

进一步展开：当前仍然存在的回归

回归主要来自错误拒绝可执行操作、跨订单状态绑定、不可逆动作顺序和参数选择。它们说明当前的 turn 级奖励只能改善一部分写操作决策，还不能稳定解决全部长链路推理问题。

进一步展开：结论边界

当前结果是方向性的数值提升，不能声称统计显著或全面优于 Vanilla；Vanilla step100 与 Anchored step80 也包含 checkpoint 选择差异。测试集已经用于错误分析，后续若继续调整算法，需要使用新的未分析数据确认。

04 · 数据构建：先获得可学习的工具轨迹

讨论记录 · 2026.09.05 · 第一轮梳理

这一阶段的目标，是给学生模型提供完整的多轮工具使用示范：什么时候追问用户、 什么时候查询信息、怎样组织工具参数，以及执行后如何继续对话。训练样本的基本单位是一条完整轨迹， 其中包含多轮消息和工具执行结果；256 条轨迹不等于 256 条单轮问答。

4.1 项目里怎么做：谁产生了数据？

从官方 Retail 的 74 个训练任务中固定划出 64 个训练任务和 10 个验证任务， 官方 40 个测试任务另行保留。本次 SFT 数据采集只使用这 64 个训练任务。 DeepSeek Flash 分别承担两个角色：User Simulator 根据隐藏的用户任务与 Agent 对话； Teacher Agent 根据可见对话和业务规则回复或发起工具调用。工具返回由 Retail 环境实际执行产生， 不是让 Teacher 编造一段工具结果。

每个训练任务采集 8 条轨迹，共 512 条。Teacher Agent 使用 0.2、0.6、0.9 三档温度， 每任务分别采集 2、4、2 条；用户模拟器温度为 0.0。这样既保持任务覆盖， 也获得不同表达和工具路径的候选。低温度不能保证外部 API 完全确定，用户模拟器仍可能偏离任务。

4.2 从候选到训练数据：先记住这条主线

512 条候选 → 451 条硬检查通过 → 435 条语义接受 → 256 条最终入选

硬检查确认终局结果及结构要求；Teacher 语义检查进一步核对用户意图、业务确认过程和回复一致性； 最终选择兼顾质量、任务覆盖与多样性。256 条数据覆盖全部 64 个任务， 每任务实际保留 2～8 条，并不是固定各留 4 条。

这里的“干净”同时指质量筛选与格式整理。通过筛选不代表每一步都无错误： 最终仍有 12 条带工具错误复查标记的轨迹。整理后的模型输入保留 System、User、Assistant、Tool 消息与工具 Schema，排除隐藏任务答案和验证器参考信息。具体保留与删除规则下一次再展开。

4.3 为什么这样做，以及取舍

终局成功并不能保证过程适合模仿，因此不能仅按 reward=1 选 SFT 数据。 增加语义检查可以发现确认遗漏、用户任务失真及最终回复不一致，但也引入 Teacher 的判断误差和 API 成本。 目前记录支持这些筛选确实执行过；还没有据此证明每一项筛选都独立提高了模型表现。

4.4 面试表述草稿

我们先在 64 个训练任务上采集 512 条多轮交互轨迹，由模型分别扮演用户和示范 Agent， 工具由真实环境执行。考虑到终局成功不保证过程质量，再经过硬检查、语义筛选以及覆盖和多样性选择， 得到 256 条 SFT 轨迹。之后才进入消息标准化、模板渲染、分词和监督 mask 构建。

证据：数据构建阶段总结； 最终选择统计； 任务划分。 本节记录项目实际流程，个人负责的设计与实现范围将在简历表述定稿时确认。
