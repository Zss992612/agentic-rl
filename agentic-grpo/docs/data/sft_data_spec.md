# Retail SFT 数据方案

本文档记录 Retail 任务划分、候选轨迹采样和正式 SFT 数据筛选方案。

## 1. 官方数据来源

官方任务划分来自：

```text
tau2-bench/data/tau2/domains/retail/split_tasks.json
```

Retail 共包含：

- 官方 Train：74 个任务。
- 官方 Test：40 个任务。
- Base：114 个任务。

本项目只从官方 74 个 Train 任务中继续划分训练集和验证集。官方 40 个 Test 任务保持不变，不参与数据构建、调参或 checkpoint 选择。

## 2. 项目任务划分

### Train：64 个任务

```text
0, 1, 2, 3, 4, 6, 7, 8,
10, 11, 13, 14, 15, 16, 19, 20,
21, 22, 23, 25, 28, 29, 30, 31,
34, 35, 37, 46, 47, 48, 57, 59,
63, 66, 67, 69, 72, 75, 76, 78,
80, 81, 82, 83, 84, 85, 87, 89,
91, 92, 93, 95, 96, 98, 99, 103,
104, 105, 106, 107, 109, 110, 112, 113
```

用途：

- 生成 SFT 候选轨迹。
- 构造正式 SFT 训练集。
- 后续用于 GRPO 在线 rollout 和参数更新。

### Validation：10 个任务

```text
24, 41, 43, 44, 50, 52, 54, 58, 73, 88
```

用途：

- 训练过程中进行任务级在线评测。
- 选择 checkpoint 和调整超参数。
- 检查模型是否只记忆训练任务。

Validation 任务不得加入 SFT 或 GRPO 训练，也不得用其 reward 更新模型参数。

### 官方 Test：40 个任务

```text
5, 9, 12, 17, 18, 26, 27, 32,
33, 36, 38, 39, 40, 42, 45, 49,
51, 53, 55, 56, 60, 61, 62, 64,
65, 68, 70, 71, 74, 77, 79, 86,
90, 94, 97, 100, 101, 102, 108, 111
```

用途：

- 最终比较 Base、SFT 和 GRPO。
- 不用于数据筛选、超参数调整或 checkpoint 选择。

## 3. Validation 选择原则

Validation 不是随机抽取最后 10 个任务，而是根据任务结构分层选择。

任务类型覆盖：

| 类型 | Task ID | 数量 |
|---|---|---:|
| 换货 | 52、58 | 2 |
| 退货 | 54、73 | 2 |
| 修改待处理商品 | 41、44 | 2 |
| 取消订单 | 88 | 1 |
| 地址修改 | 43 | 1 |
| 查询/不写数据库 | 24 | 1 |
| 转人工 | 50 | 1 |

难度覆盖：

| 难度 | Task ID | 数量 |
|---|---|---:|
| 简单 | 44、50、73 | 3 |
| 中等 | 24、43、52、88 | 4 |
| 困难 | 41、54、58 | 3 |

划分时避免将高度相似的模板变体拆到 Train 和 Validation 两侧。复杂度主要依据标准动作数、写操作数、多商品、多订单和条件分支估计。

## 4. SFT 候选轨迹采样

只对 64 个 Train 任务进行 SFT 候选轨迹采样。

每个任务采样 8 条候选轨迹：

| 采样档位 | 每个任务数量 |
|---|---:|
| 低随机性 | 2 |
| 中随机性 | 4 |
| 高随机性 | 2 |
| 合计 | 8 |

总候选数量：

```text
64 × 8 = 512 条
```

三档只表示 Agent 解码随机程度，不表示业务行为应更加激进。第一版保持用户模拟器参数稳定，将主要多样性放在 Agent/Teacher 侧。具体 temperature 和其他解码参数在 Pilot 后固定。

## 5. 正式 SFT 数据目标

每个任务从 8 条候选中最多保留 4 条：

```text
64 × 4 = 最多 256 条正式 SFT 轨迹
```

256 是目标上限，不强制为每个任务凑满 4 条。质量不足时记录缺口并决定是否补采样，不使用低质量轨迹填充数量。

筛选必须在每个任务内部进行，不能从全部 512 条中直接全局选择 256 条，否则简单任务可能占据大部分数据。

## 6. 轨迹筛选原则

### 硬性过滤

- simulation 运行完整，不是基础设施错误。
- 用户模拟器遵守任务指令，没有明显遗漏或错误改变意图。
- 不存在任务完成前提前输出 `###STOP###`。
- 官方 Verifier 成功。
- 工具调用格式和参数合法。
- 写数据库前获得明确用户确认。
- 最终回复与工具执行结果一致。
- 不存在明显的 Retail policy 违规。

### 质量与多样性选择

- 工具调用路径正确且不过度冗余。
- 对话表达自然。
- 保留不同但合理的询问和恢复路径。
- 删除完全相同或高度重复的轨迹。
- 在质量合格的前提下，尽量保留不同采样档位。

## 7. Pilot 验证

正式采样 512 条之前，先选择 4 个代表性 Train 任务进行 Pilot：

```text
4 个任务 × 8 条候选 = 32 条候选轨迹
```

Pilot 需要验证：

- 三档采样是否产生有效多样性。
- 用户模拟器异常能否被识别。
- 筛选规则能否发现 reward 假阳性和假阴性。
- 每个任务是否能保留约 4 条高质量轨迹。
- 轨迹能否转换为目标 7B 模型的 chat template 和 assistant-only loss mask。

Pilot 通过后再进行完整的 64 × 8 采样。

## 8. 固定与变更原则

- 当前 64/10/40 划分确定后保持固定。
- 如发现任务定义或 Verifier 存在明确缺陷，先记录证据，再决定是否调整。
- 任何任务划分变更都要记录原因和版本，不能根据模型评测结果临时更换难题。
- 后续机器可读的任务列表将单独保存在 `training/configs/data/retail_split.yaml`，供采样、训练和评测脚本共同读取。
