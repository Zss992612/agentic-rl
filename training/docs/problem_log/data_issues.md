# Agentic RL 数据与轨迹质量问题记录

本文档只记录由数据、用户模拟器、轨迹质量和数据有效性引起的问题，以及这些问题的成因、影响、解决方案和验证方法。工程实现问题和算法设计问题后续分别记录在其他文件中。

记录原则：

- 官方 benchmark 指标保持原始口径，不删除失败样本。
- 人工审计结果作为补充诊断指标单独报告。
- 区分 Agent、用户模拟器、环境、Verifier 和基础设施问题。
- 解决方案实施后，补充实际验证结果，不只记录预期效果。

## 问题 001：用户模拟器改变意图过晚

### 相关任务

Retail Task 5。

### 现象

任务要求用户在多次确认过程中逐步改变意图，最终放弃换货并退回水瓶。

实际运行中，用户先明确确认只更换台灯。Agent 完成不可逆的换货工具调用后，用户才提出取消台灯换货并改为退回水瓶。最终数据库状态与任务期望不一致，Verifier 给出 `reward=0`。

### 可能成因

- 用户模拟器没有准确执行隐藏任务中的条件分支。
- 用户模拟器对“选择商品”和“最终确认”的语义区分不稳定。
- 多层条件指令对模型的指令遵循能力要求较高。
- Agent 将付款方式询问和最终确认合并在一条消息中，增加了用户模拟器判断确认阶段的难度。

### 影响

- Agent 在可观察信息下行为基本合理，却获得负奖励，形成假阴性 reward。
- 如果直接用于 GRPO，可能错误降低合理行为的概率。
- 该轨迹不适合作为 SFT 正样本。
- 原始成功率会同时包含用户模拟器稳定性的影响，不能完全等价为 Agent 能力。

### 解决方案

- 在数据审计时将该类轨迹标记为 `user_simulator_failure`。
- SFT 数据中排除用户意图表达时序错误的轨迹。
- GRPO 训练前检测明显的模拟器异常，并采用重试或单独记录，而不是直接当作 Agent 负样本。
- 训练阶段可将复杂条件任务重复采样多次，评估模拟器的一致性。
- 后续研究是否将确认过程拆成更清晰的独立消息，但官方评测仍保留原始环境设置。

### 验证方式

- 对 Task 5 使用相同配置重复运行多次。
- 检查用户是否在正确的确认轮次表达最终意图。
- 分别统计原始 pass@1 和用户模拟器有效轨迹上的 Agent pass@1。

## 问题 002：用户模拟器提前终止任务

### 相关任务

Retail Task 8。

### 现象

Agent 已找到正确订单、台灯型号、付款方式和价格差，并向用户请求最终确认。用户在确认换货的同一条消息中输出了 `###STOP###`。

环境因此立即以 `user_stop` 结束 simulation，Agent 没有机会调用最终的 `exchange_delivered_order_items`，数据库没有被修改，Verifier 给出 `reward=0`。

### 可能成因

- 用户模拟器把“已经确认操作”误判成“任务已经完成”。
- 用户模拟器没有区分用户确认和环境实际执行成功。
- 终止条件只依赖特殊字符串，没有验证目标数据库状态是否已经达成。
- 用户模拟器还提前省略了初始水瓶需求，说明其隐藏指令遵循不完整。

### 影响

- 正确的 Agent 计划在执行前被中断。
- GRPO 会把环境中断产生的失败错误归因给 Agent。
- 轨迹无法作为完整的 SFT 工具调用样本。
- 任务耗时更短，但这种耗时不代表任务更简单或 Agent 更高效。

### 解决方案

- 将“确认后立即 STOP、但目标写工具尚未执行”识别为无效终止。
- 训练数据采集时对此类轨迹进行重试并保留异常原因。
- 单独记录 `premature_stop_rate`，评估用户模拟器可靠性。
- 如后续增加终止保护，应只用于训练稳定性实验；官方 benchmark 评测继续使用官方终止逻辑。

### 验证方式

- 重复运行 Task 8，检查 `###STOP###` 是否稳定出现在工具成功之后。
- 对所有失败轨迹检查：最终用户消息是否包含 `###STOP###`、目标写工具是否已经执行、数据库是否已达到目标状态。

## 问题 003：Agent 违反工具调用过程规范

### 相关任务

Retail Task 5 和 Task 8 均出现。

### 现象

- Agent 在一个 assistant turn 中并行调用多个工具。
- Agent 在同一个 turn 中同时输出自然语言和工具调用。

Retail policy 要求一次最多调用一个工具，并且工具调用和用户回复不能同时发生。

### 可能成因

- 模型或 API 默认支持并偏好多工具并行调用。
- 当前执行入口没有对单次工具调用数量进行强约束。
- 仅依靠 system prompt 约束，不能保证模型始终遵守格式。

### 影响

- 轨迹过程违反官方环境 policy。
- reward 只检查最终数据库时，这类违规可能仍获得 `reward=1`，形成假阳性。
- 如果进入 SFT 数据，会把违规调用模式教给学生模型。

### 解决方案

- 在 SFT 审计中加入单工具调用和消息互斥检查。
- 评测时单独统计 `multi_tool_call_rate` 和 `text_with_tool_call_rate`。
- 后续训练接入时研究在执行层拒绝或顺序化非法工具调用。
- 第一版保留官方 reward，同时增加过程合规指标，避免改变基线口径。

### 验证方式

- 扫描每个 assistant turn 的 `tool_calls` 数量。
- 检查带有 `tool_calls` 的消息是否同时包含非空 `content`。
- 对比加入约束前后的过程合规率和最终任务成功率。

## 问题 004：Verifier 对过程错误覆盖不足

### 现象

Task 5 和 Task 8 的 `reward_info` 主要由最终数据库匹配结果决定。Agent 的多工具调用、文本与工具同时输出等违规没有进入 reward。

### 可能成因

- 当前任务的有效检查集中在最终 DB 状态。
- `action_checks`、自然语言断言或过程断言在这些任务中没有提供有效惩罚。
- 官方 Verifier 更关注任务是否完成，而不是完整的行为质量。

### 影响

- 最终状态正确但过程违规的轨迹可能得到满分。
- 最终状态错误但 Agent 决策合理的轨迹可能得到零分。
- 单一 reward 无法支持细粒度的信用分配和故障归因。

### 解决方案

- MVP 阶段保持官方 Verifier 不变，确保结果可比较。
- 在官方 reward 之外增加只用于诊断的过程指标。
- 后续算法实验可研究由结果奖励和过程合规奖励组成的混合奖励。
- 所有新增奖励都需要通过消融实验与官方 reward 基线比较。

### 验证方式

- 人工抽查 reward=1 的轨迹，统计其中的过程违规率。
- 比较官方 reward、过程合规分数和人工判断之间的一致性。
- 检查新增过程奖励是否提升真实成功率，而不是只优化表面格式。

## 问题 005：多组件交互造成奖励噪声

### 现象

在多轮 Agent 环境中，最终 reward 不只由 policy model 决定，还受到用户模拟器、工具环境、终止逻辑、API 和 Verifier 的共同影响。

### 影响

- GRPO 可能把其他组件的错误归因到 Agent token 上。
- 同一个任务的多次 rollout 可能因为环境噪声获得不同奖励。
- 组内 reward 方差不一定完全代表 Agent 行为质量差异。

### 解决方案

- 为每条失败轨迹记录统一归因标签：`agent`、`user_simulator`、`environment`、`infrastructure`、`verifier` 或 `mixed`。
- 同时报告原始指标和人工审计后的诊断指标。
- 对明显的基础设施或模拟器异常采用有限重试，并记录重试次数。
- 训练时监控 group reward、零方差组比例和异常终止比例。

### 验证方式

- 对相同任务进行多次采样，计算 reward 一致性。
- 分别统计各类失败原因的数量和比例。
- 对比过滤明显无效 rollout 前后的 GRPO 学习曲线。

## 问题 006：基础设施错误与模型失败混在运行结果中

### 相关任务

Retail Task 77。

### 现象

Task 77 的 `termination_reason` 为 `infrastructure_error`，运行时长为 0，没有消息轨迹和 reward。

### 影响

- 如果直接按 114 个任务计算成功率，会把基础设施错误当成模型失败。
- 如果直接删除又不报告，会使评测结果失去透明度。

### 解决方案

- 原始指标按全部任务报告。
- 同时报告排除基础设施错误后的有效运行指标。
- 单独记录基础设施失败数量、错误类型和重试结果。
- 重试成功后保留原始错误记录，避免覆盖故障证据。

### 验证方式

- 检查重试后是否能正常生成完整轨迹。
- 确认失败与模型输出无关，再归类为基础设施问题。

## 当前初步统计

- Retail 总任务数：114。
- `reward=1`：103。
- `reward=0`：10。
- 基础设施错误：1（Task 77）。
- 全部任务口径成功率：`103 / 114 = 90.35%`。
- 排除基础设施错误后的成功率：`103 / 113 = 91.15%`。

以上仍是初步分析。后续完成其余失败任务审计后，再更新归因数量和最终结论。

## 对 SFT 数据构建的整体影响

### 核心结论

不能只使用 `reward == 1` 作为 SFT 数据的筛选条件。

官方 reward 主要反映任务最终状态是否满足 Verifier，但一条 `reward=1` 的轨迹仍可能包含违规工具调用、错误确认流程或不完整的用户表达。如果直接用于 SFT，学生模型会同时模仿这些错误行为。

因此，`reward=1` 只能作为候选轨迹的第一层条件，而不是最终录用标准。

### 建议的轨迹审计流程

1. **运行有效性检查**
   - 排除 API、基础设施和环境初始化失败。
   - 排除没有完整消息或异常中断的轨迹。

2. **用户模拟器检查**
   - 用户是否表达了任务要求中的关键信息。
   - 用户是否在规定的阶段改变意图。
   - `###STOP###` 是否发生在任务真正完成之后。
   - 用户是否编造了隐藏任务中不存在的信息。

3. **任务结果检查**
   - 官方 Verifier 是否成功。
   - 最终数据库状态是否符合目标。
   - Agent 的最终回复是否与工具执行结果一致。

4. **过程合规检查**
   - 是否完成身份认证。
   - 写数据库前是否列出操作详情并获得明确确认。
   - 每个 assistant turn 是否最多调用一个工具。
   - 是否避免在同一条消息中同时输出文本和工具调用。
   - 工具名称、参数、商品 ID 和订单 ID 是否正确。

5. **训练格式检查**
   - 消息能否正确渲染为目标 7B 模型的 chat template。
   - loss mask 是否只覆盖 assistant 文本和 assistant 工具调用。
   - system、user 和 tool observation 是否被正确屏蔽。

6. **多样性与重复检查**
   - 删除完全相同或高度重复的轨迹。
   - 保留不同但合理的询问、恢复和工具调用路径。
   - 避免少量任务模板在数据集中占比过高。

### 数据处理产物

每条候选轨迹应保留：

- 是否被录用。
- 被排除的具体原因。
- 官方 reward。
- 人工或规则审计标签。
- 用户模拟器是否有效。
- Agent 过程是否合规。
- 轨迹长度、工具调用数量和任务类型。

这部分可以作为项目中的独立工作量描述：构建面向长链路工具 Agent 的轨迹审计与 SFT 数据处理流程，而不是简单收集所有成功轨迹。

## 对 GRPO 训练的整体影响

### 假阴性奖励

假阴性表示：

```text
Agent 的决策本来正确
但用户模拟器、环境或基础设施出现问题
最终 reward = 0
```

Task 8 就是典型例子。Agent 已经确定正确商品和支付方式，但用户模拟器提前输出 `###STOP###`，导致目标工具无法执行。

在 GRPO 中，这条轨迹可能得到负的组内 advantage，使模型降低原本合理行为的生成概率。

### 假阳性奖励

假阳性表示：

```text
Agent 的过程中存在错误或 policy 违规
但最终数据库状态碰巧正确
最终 reward = 1
```

例如 Agent 在一个 turn 中并行调用多个工具，但 DB Verifier 只检查最终状态。这种轨迹可能获得满分，使 GRPO 提高违规行为的概率。

### 对组内相对优势的影响

GRPO 根据同一个任务的多条 rollout 计算组内相对优势。简化表示为：

```text
advantage = (当前 reward - 组内平均 reward) / 组内 reward 标准差
```

因此奖励噪声不仅影响一条轨迹，还会改变同组其他轨迹的相对排序：

- 假阴性会把正确轨迹排到错误轨迹附近或下面。
- 假阳性会把违规轨迹排到合规轨迹附近或上面。
- 如果噪声导致同组 reward 全部相同，组内 advantage 可能接近零，当前任务无法提供有效更新。
- 如果不同 rollout 的差异主要来自用户模拟器，而不是 Agent，GRPO 学到的就不是真正的 Agent 行为差异。

### MVP 阶段的处理原则

- 保留官方 Verifier reward，作为可复现的主训练信号和基线。
- 不静默删除官方评测中的失败样本。
- 对 rollout 增加组件级诊断标签，区分 Agent、用户模拟器、环境、基础设施和 Verifier 问题。
- 对明确的基础设施失败和明显的提前终止进行有限重试，并记录原始错误和重试次数。
- 监控假阴性、假阳性、异常终止率和组内零方差比例。
- 只有明确无法形成有效交互的 rollout 才考虑从训练批次中剔除，避免根据最终 reward 主观挑选样本。

### 后续算法改进方向

- 在官方结果奖励之外增加过程合规信号。
- 将最终 DB reward 与确认、工具调用和终止有效性组成混合奖励。
- 研究 action-level 或 turn-level 的信用分配，减少最终标量奖励对整条长轨迹的粗粒度归因。
- 通过消融实验分别比较官方 reward、异常轨迹处理、过程奖励和完整方案。

这部分可以形成项目中的算法问题描述：多轮 Agentic RL 的 reward 会受到外部交互组件污染，需要识别假阴性和假阳性，并研究更可靠的轨迹有效性判断与信用分配方法。

## 问题 007：用户模拟器温度与用户表达多样性

### 问题背景

当前正式 SFT 轨迹采集将用户模拟器的 `temperature` 设为 `0`。同一任务重复采样时，用户的初始表达和后续回复可能较为相似，因此需要判断模型是否会只适应固定的用户表达方式。

需要注意，SFT 中的 user token 虽然不计算 loss，但仍会作为上下文输入模型。模型学习的是在 system、user 和 tool observation 条件下生成 assistant 回复及工具调用，而不只是学习固定的回答模板。

### 可能成因

- `temperature=0` 会减少同一任务内用户措辞和交互方式的随机性。
- 每个任务重复采样多次，可能放大相同用户表达的占比。
- 如果 Agent 回复和工具路径也高度相似，会形成低价值的重复轨迹。
- 训练数据规模较小时，有限的用户表达覆盖可能造成分布偏移。

### 对 SFT 的可能影响

- 模型可能更擅长训练集中出现过的用户措辞，对同义改写、不同确认方式和不同追问方式不够稳定。
- 高度重复的轨迹会重复强化少数交互模板，降低有限训练数据的有效多样性。
- 但当前 64 个训练任务本身包含不同需求，而且不同 Agent 输出会引起不同的后续用户回复，因此 `temperature=0` 不等于所有轨迹完全相同。
- Base 模型已经具有一定的自然语言改写理解能力，所以当前 512 条轨迹仍可用于建立第一版稳定的 SFT 基线，无需重新采集。

### 对 GRPO 的可能影响

- User temperature 非零可以增加措辞、追问、确认方式和交互长度的多样性，提高策略的交互鲁棒性。
- temperature 过高可能导致用户改变原始意图、前后矛盾或提前停止，产生任务漂移。
- 同组 rollout 的 reward 差异可能来自用户模拟器随机性，而不是 Agent 行为，使 GRPO 的相对优势包含额外噪声。
- 用户模拟器异常可能造成假阴性奖励，并把错误信用分配给 Agent token。

### 当前解决方案

- 保留现有 SFT 数据的 `user_temperature=0`，优先获得稳定、可审计的行为示范。
- SFT 去重不只比较用户文本，重点比较 Agent 回复、工具名称、参数、调用顺序和最终回复。
- 对高度相似的 Agent 行为轨迹降低保留数量，避免同一任务模板权重过高。
- 第一版 GRPO 暂定使用 `agent_temperature=0.7`、`user_temperature=0.2`，在 Agent 探索和用户稳定性之间折中。
- 不把 RL 当作解决用户表达泛化的唯一手段；先通过独立评测确认问题是否真实存在。

### 验证与后续处理

- 标准评测固定使用相同的低随机配置，例如 `user_temperature=0`，公平比较 Base、SFT 和 GRPO。
- 增加用户表达鲁棒性评测：保持任务目标不变，通过受控改写或 `user_temperature=0.2～0.3` 改变用户表达。
- 比较标准表达与变化表达下的任务成功率、过程合规率和异常终止率。
- 如果 SFT 在表达变化后明显下降，再为约 `10%～20%` 的训练任务补充受控用户改写数据，而不是重新采集全部轨迹。
- 后续对比不同 User temperature 下的任务意图保持率、reward 一致性和 GRPO 组内零方差比例。
